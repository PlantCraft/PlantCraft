# Devlog

Notes on how the module changed and why, newest first: what a later contributor would need to
know that the code and `CHANGELOG.md` do not say. One short entry per change worth explaining.

## Unreleased

- Demo assistant without credit (2026-11-01): the OpenAI account ran out of credit during the model bake-off and every call answered 429. A visit now reads a plain sentence instead of the service's error (which names keys and settings), the failed question does not count against the visit's ten, and a 401/403/429 pauses visits' questions for 10 minutes per server process (in memory: each worker learns it on its own first failure). `ChatModel` raises `ModelServiceError` with the HTTP code.
- `plantcraft llm set|show` (2026-11-01): sets a provider and the default model from the server's shell, with the key read from stdin or a file (never argv, so not in shell history or `ps`); the same store calls as Setup › Language models, plus the egress allowlist and an audit entry (actor `cli`). Lets a deploy turn the demo's assistant on without a browser session.
- Assistant prompt caching (2026-11-01): the instructions now keep what is the same for every question first (rules, tools' guidance) and what changes last (who asks, the time, the page's context, the question's language). Before, the person's name opened the instructions and the clock sat in the middle, so no two questions shared a cacheable start beyond the tools. OpenAI requests carry a `prompt_cache_key` derived from the offered tools' names, Anthropic requests mark the tools and the instructions with `cache_control`. A chat with nothing to create is told so in one line instead of the card rules, and a demo visit gets a short-answer rule (about 150 words). `meta.usage.cached` shows the effect per answer.
- Lists inside JSON get side tables (2026-10-31): `plantcraft.db.list_index` keeps `app_run_subjects` and `app_knowledge_subjects` (one row per subject) by triggers on `app_runs` and `app_knowledge`, filled once for existing databases. With 200,000 runs of 1 to 20 subjects each, an asset's runs (asset page, assistant facts) went from 246 ms to 3.3 ms and the texts about a reference from 10.5 ms to 0.14 ms; a run write costs 0.62 ms instead of 0.19 ms and the file grows from 79 to 162 MB in that heavy case (90-day retention bounds it). Alarms' flood count reads its 10-minute window through a new index on `outbox(at)`: 4-15 ms to 0.08 ms a person with 300,000 notices (`ci/bench/storage/json_list_bench.py`, `flood_count_bench.py`).
- Notification feed index (2026-10-31): `idx_conversation_notices`, a partial index on `conversation_messages(conversation_id, created_at)` where `meta_json` says `kind = notification`. With 300 people and a year of notifications (620k messages) `notices_for` went from 9.7 ms to 0.27 ms (p95 16.7 -> 0.47 ms); the file grows 23 MB (83 -> 106 MB) and an existing database builds it in 0.8 s at start. The other JSON filters (`json_each` over results' subjects, knowledge, Alarms' recipients) look inside arrays, which an expression index cannot hold: they need a side table if those lists grow (`ci/bench/storage/json_index_bench.py`).
- Operations (built-in, like Desk): Docker's CPU is a percentage of one core, so an "80 %" alert
  on it meant nothing for an app limited to 4 CPUs; the installer now gives each service its limit
  and the share of it, and samples the machine from `/proc`. Logs live in each app's own volume,
  which PlantCraft does not mount, so each server reads its own (`GET /api/ops/logs`) and PlantCraft
  fans out with an `ops` token instead of a log shipper: no new container, nothing leaves the
  machine. The load checks stay in the core watch, not in Alarms, so they still speak when Alarms
  is down. Requests are actions of kind `request`, not a ticket system of their own: comments,
  checklist, history, notifications and Desk come with them. A company is a kind of group, so its
  teams, coordinator, asset scope and notifications are the groups' own; its last day of access is
  checked on every request (one indexed query; the tree only once a company has ended). Hours
  count for the company of who logged them, not of the queue: what an integrator bills is their
  people's time.
- Request targets are computed when read, from the status history, not stored: a target changed
  applies at once, and nothing has to tick. The clock is the calendar's (plants run day and
  night); Blocked, an existing status, is the pause, so the API v1 status list stays as it was.
  Temporary support access adds the Operations role in `user_access` while a grant lasts (one
  indexed query per request), so every check that reads `can_operate` follows it and it ends
  without a job. Operations is not a framed app: it is left out of the frame prefixes, or `/health`
  would load the platform again inside a frame.
- Backup of the suite at one instant (2026-10-31): `plantcraft.ops.snapshot` opens a read snapshot of every SQLite file first, then copies each in one step. Before, the copy in steps of 4,096 pages restarted at every commit of another process: with 7 databases (1.5 GB) and apps committing 20 times a second it had not finished after 16 minutes; now 28 s, the same as idle, and every database holds the same instant (0.0 s apart, against minutes).
- Storage test (2026-10-31): JSON kept in each app's SQLite beats loose files (3-4x faster writes, indexable, 0/100 broken after kill -9 against 71/100 for an in-place `write_text`); one shared SQLite halves throughput and makes one app's batch stall the others' writes (p99 4 -> 54 ms, 130 ms with a heavy writer); PostgreSQL with a schema per app costs ~60 us a query against ~4 us. Kept one SQLite per app; Models writes its JSON files atomically. Benchmarks in `ci/bench/storage/`.
- Review of main after the 2026-10-31 test day (frozen at `fabcdc8`, SDK 0.92.0, ui 0.94.0): every app, the template and the platform vendor the same SDK and ui, and the wheels match `sdk/python`. Analytics' tests count the Signal quality checks from the catalog (`linkcraft.catalog.signal_checks.CHECKS`, and the API in the e2e journey) instead of a fixed number, which broke twice that day (#79, #85). The Historian's gateway token and client certificates and Models' state files use `plantcraft_sdk.files.write_atomic` (Models' `modelcraft.atomic` re-export is gone). The changelogs got the entries nine of the day's pull requests left out (security test fixes, backup at one instant, feed index, Virtual sensor, stiction shape test, View's assistant sections and calendar periods) and Keep a Changelog's section order.
- Assistant in the public demo (2026-11-01, front A of the LLM-in-the-demo plan): `PLANTCRAFT_PUBLIC_DEMO_LLM=on` lets visits ask the model, in chats owned by `demo#visit:<id>` (the account every visit shares would have shown one visit's chats to the next), ask-only (no create tools, works or specialists), 4 tool rounds, 16 tool calls and 12 turns per answer, 200 reads per visit, 1,200-character questions, 4,000-character answers with images, raw HTML and outside links removed on the server; 10 questions per visit, 6/min and 30/day per address, 600/day in all, counted in `assistant_demo_questions` (a store marked `DEMO_SHARED` for per-visit databases). Every answer now keeps the model's tokens in `meta.usage` (`specialists.model.usage_of`: Responses, chat completions, Messages), and `/api/demo/stats` sums the visits' tokens of the day. `VISIT_OWNER` moved to `plantcraft.auth.public_demo`. The panel and Desk's Assistant count a visit's questions down ("7 of 10 questions left in this demo visit"), take at most its characters, and show the team's seeded chats as read-only (`can_ask`).
